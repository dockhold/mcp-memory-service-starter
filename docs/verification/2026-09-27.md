## Design points that did not survive contact

* **`umask 077`.** The first version kept every file owner-only. A start
  under another user in the same group then could not open the databases.
  Now `umask 007`, and both databases are created empty before upstream
  opens them, because SQLite creates a database as 0644 and copies that
  mode to its `-wal` and `-shm` files.
* **A read-only `HOME` in the image.** It worked, but onnxruntime logged
  "Failed to persist telemetry device ID" at every start. `HOME` is now on
  App storage and the model is linked in from the image.
* **"mode: semantic" as proof the model loaded.** With the model link
  removed, the first start still stored and found a memory in "semantic"
  mode on hash pseudo-vectors, and only the restart failed. Hence
  `MCP_MEMORY_ALLOW_HASH_EMBEDDINGS=0`; with it the same control fails at the
  first store.
* **`isError` as proof a store worked.** Upstream reports a failed store with
  `isError: false`. The test now requires the success text.
* **Refusal checks that only looked at the exit code.** The half-key-pair
  case "passed" because the app refused for a different reason (no public
  address). Every refusal now has to print its own line.
* **Deleting files on storage to sign clients out.** Nobody has a shell on
  App storage. Changing the API key now does it.

## Local results

`tests/smoke.sh mcp-memory-service-starter:test`: 15 passed, 0 failed.
Healthy 6 to 7 s after start, about 205 MiB in use after a store and a
search, stops on SIGTERM in 0 to 1 s with exit code 0.

Controls, each run with one fix removed from the start script:

| Removed | Expected | Result |
| --- | --- | --- |
| the model link | the first store fails | `FAIL memory_store` |
| the sign-out on a key change | the old token still works | `FAIL the old access token is refused (401) [200]` |
| `MCP_OAUTH_TRUST_PROXY_HEADER` | every visitor shares one limit | `FAIL a second visitor is not affected ... [429]` |
| the pre-created databases (first version) | a start under another user in the group cannot write | registration answered 500 |

Security review by a second reader: no high or medium findings. Applied from
it: refuse half a key pair, `HOME` set by the start script, `set -f` around
the model fetch, and the README line that the API key is also a bearer
credential.

the Deploy form's defaults: 256 MB, App storage 10 GB, one secret bound as
`MCP_API_KEY`. Client steps ran `tests/flow.py` from a workstation against
the app's `https://<app>.dockhold.app` address.

| Step | Result |
| --- | --- |
| Build on Dockhold from the `Dockerfile` | built and started |
| First start with no App storage | refused; the app log showed the one storage line from the README |
| App storage turned on, no secret yet | restarted by itself, refused with the `MCP_API_KEY` line |
| Secret bound, **Restart** | `/health` answered `{"status":"ok"}` |
| `probe login store search` | all passed; the OAuth issuer is the app's `https://` address |
| `edge`: 70 login requests with a made-up `X-Forwarded-For`, then one with another made-up address | the second is still limited (429): the edge sets the header, so a client cannot choose its own address. That each real visitor gets its own limit is shown by the local `ratelimit` step only; it needs a second real client address. |
| **Restart** (with App storage: stop, then start) | reachable again after about 20 s; the access token from before still works and the memory is found in semantic mode |
| Push of a new commit (`8be776d`), deployed by Dockhold's auto-deploy | the access token from before the deploy still works and the memory is found in semantic mode |
| Log after the restart | upstream's slim-image warnings only (see README, Limitations); no error, no key value, no "failed to persist" |

Not run in production: changing the API key (it needs a change in the
dashboard; covered by the local suite), and the free plan's image limit

when the image passes it).
